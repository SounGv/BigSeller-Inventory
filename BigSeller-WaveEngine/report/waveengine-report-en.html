WaveEngine Operations Report

A bot that confirms new orders and builds picking waves in BigSeller, by driving the real web UI. This is what one cycle does, the rules it follows, and how far it has actually been proven.

01What it replaces

Two jobs staff do by hand all day. First, confirming new orders one screen at a time, in an order that only exists in people's heads — the two-hour Shopee channel before the standard Lazada round, and so on. Second, opening the WMS and generating picking waves for whatever has piled up.

Neither step has an API. The engine does what a person does: opens the page, sets the filters, reads the counts, and clicks. That is why almost every rule below is a rule about not clicking.

02One cycle, start to finish

A cycle runs on the order queue and, if anything was confirmed, continues into the wave page. Any gate that cannot be verified ends the cycle instead of guessing — the red bars are the points where the engine deliberately stops.

1

Read the queue's own counts

BigSeller already counts the queue by courier, store, platform and warehouse. Reading those filter numbers answers “what do I confirm first” without walking a single row.

~2 seconds · read only · --board

2

Collect the reservation list

Filter to the LockStock store and collect its order ids. A row never says which store it came from, so this is the only way to know which orders are stock a salesperson is holding rather than something to ship.

FAIL CLOSEDIf that list cannot be read, the whole cycle is abandoned. Confirming a reservation would ship goods held for another customer.
3

Scan the picking warehouse

Pin the warehouse filter to STOCK_5, verify it took, then walk every page — deduplicating by order id, because staff are confirming orders at the same time and rows shift backwards between pages while the bot paginates.

VERIFYRow count is checked against the filter's own figure. A structurally broken scan (one page of six) ends the cycle rather than acting on a partial queue.
4

Decide, per order

Each order resolves to a channel, then to a priority and a timing rule — act now, wait for its truck, hand to a human, or skip entirely. Every decision is written to an audit line with the reason that produced it.

pure logic · no page access · 141 unit tests cover this step

5

Confirm, in priority order

Only orders whose priority is explicitly enabled are clicked, most urgent first, capped per cycle. Each row is re-read immediately before its click, and the result is proven three ways — the row leaves the list, its confirm control disappears, or its status stops reading as new.

NEVER TWICEAn order already attempted in this cycle is never clicked again, and an unverified click is logged as unverified, never as success.
6

Build waves — one carrier at a time

For each courier that actually had an order confirmed: pin the warehouse, set the courier as the only scope, and open the preview. BigSeller splits it into rows — one per floor, per pick method — and each row becomes its own wave.

ONE CARRIERThe scope is asserted to cover exactly one courier before anything can be created. Waves never mix carriers.
7

Select only the rows worth a trip

Cross-floor rows are dropped and reported. Rows under their size threshold are held for the next cycle. What remains is ticked, the selection count is verified against the table, and the wave is created.

HAND BACKThe courier tree is reset afterwards, so the next person to open the page is not handed a narrow scope the bot left behind.

04What makes a wave worth creating

A wave is one picking trip to one floor. FANTECH is floor 5, Ugreen is floor 3 — the zone label 3FL Ugreen says so outright. That single fact sets every rule here.

SINGLE-SKU ROW 50 parcels

Grab-and-pack, so one round clears many.

MULTI-SKU ROW 20 parcels

Picked and sorted per order — the same round holds far fewer.

SHORT LOAD 30 minutes

Collected per courier, then sent as one batch rather than a wave per order.

Live wave, 11 Sep: 2 · 1 · 24 · 2 · 2 parcels

Five separate trips for 31 parcels — four of them climbing a floor for one or two items. That run is why the thresholds above exist. Under the current rules the same queue produces one trip, not five.

05What it will never do

  • RESERVED

    Touch a LockStock order. Those are reservations held for a named customer, excluded before the decision, again at classification, and once more immediately before the click.

  • WRONG STOCK

    Confirm an order outside STOCK_5. Anything else needs a human to move goods first — and the engine never moves stock itself.

  • CROSS-FLOOR

    Put a cross-floor row in a wave. Filling one means a picker walking between floors 5 and 3 for a single order, so those rows are reported and left alone.

  • MIXED

    Create a wave covering more than one courier, or confirm the same order twice in a cycle.

  • SELF-ENABLE

    Turn on its own live actions. Every priority is off until named explicitly, one at a time.

07Open decisions

Four things are waiting on an operational answer rather than on code.

  • TIME FILTER

    BigSeller's เลือกเวลา filter is left as found, so a wave can sweep in older confirmed orders. Pinning it to วันนี้ is cleaner but risks stranding yesterday's leftovers where nobody sees them.

  • UNRANKED

    Three couriers exist in BigSeller with no priority assigned: SPX Express - ผู้ซื้อรับที่จุดบริการ, Lazada-TH-Flash TH Bulky, Shopee-TH-Best Express Bulky. They route to manual review, which is safe but unattended.

  • SHARED WAVE

    BEST Express and DHL Domestic are approved to share a wave, but the code still waves them separately and neither has had a real order to test with.

  • NO DATE

    Urgent walk-in Seller Delivery cannot be automated from the list view — the กำหนดส่ง date is not in it, so those orders always go to manual review.
